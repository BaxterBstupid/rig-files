# RealityScan "The physical end of the tape has been reached" on COLMAP Import: Definitive Cause and Fix

## TL;DR
- **The error is Windows system error 1100 (ERROR_END_OF_MEDIA)** — per Microsoft Learn's "System Error Codes (1000–1299)" in WinError.h: *"1100 (0x44C) ERROR_END_OF_MEDIA — The physical end of the tape has been reached."* RealityScan surfaces this raw OS string when its COLMAP parser hits an unexpected end-of-file while still trying to read fields it expects. It is a malformed/incomplete-model error, NOT a disk-full error. Your leading hypothesis is right in mechanism but wrong in the specific field: the header comment counts ("Number of images: 2106") are **NOT** the trigger; the real trigger is that RealityScan's importer requires a fully-consistent model with **populated POINTS2D observations in images.txt AND a matching points3D.txt with real points + TRACK data** — the empty/header-only approach fundamentally does not work.
- **The confirmed-working fix** (note.com/kozosoken guide) is to POPULATE points3D.txt with real 3D points AND rebuild the POINTS2D observations in images.txt (via a `rebuild_colmap_tracks.py` script that reprojects points into images), then re-export from COLMAP so all three files are mutually consistent. Independent Epic Developer Community reporters also traced failures to trailing spaces and trailing empty lines.
- **The robust alternative we recommend switching to** is per-image XMP sidecars with `xcr:PosePrior="locked"`, `xcr:Coordinates="absolute"`, a row-major world-to-camera `xcr:Rotation`, and `xcr:Position` set to the camera CENTER in world coordinates. This bypasses COLMAP entirely and is the officially documented Epic path for importing known, fixed poses.

## Key Findings

### 1. What the error actually is (verified)
"The physical end of the tape has been reached" is **Windows error code 1100, ERROR_END_OF_MEDIA** (Microsoft Learn, System Error Codes 1000–1299, WinError.h). RealityScan has no custom message for this failure; it passes through the raw OS error when a low-level read returns fewer bytes than requested. In the COLMAP text importer this means the parser reached EOF while still trying to read fields it expected to exist. On the Epic Developer Community forum thread "Error while opening Colmap Text Format," the Epic moderator (OndrejTrhan) initially mis-diagnosed it as a disk-full error, but the original reporter (stiv2804) confirmed 80–300 GB free across all drives and still failed — ruling out the disk-space interpretation. The reporter's log showed: *"Importing failed after 8.189 seconds. Processing failed: The physical end of the tape has been reached…"*

### 2. The header "Number of images: 2106" mismatch is NOT the cause (assessment)
COLMAP's official Output Format documentation (colmap.github.io/format.html) states verbatim: *"Comments start with a leading '#' character and are ignored. The first comment lines briefly describe the format of the text files."* The "Number of images / cameras / points" lines are comment lines beginning with `#`. Every standard COLMAP text reader (the reference `read_write_model.py`, pycolmap, instant-ngp's `colmap2nerf.py`, and the Gaussian-splatting `colmap_loader.py` variants) skips any line whose first character is `#` and counts records by reading until EOF — none parse the declared count from a comment. There is no evidence RealityScan behaves differently for text files.

Your mismatch (header says 2106, file has 422 entries) is therefore very unlikely to be the trigger. This is the correct hypothesis mechanism ("read a declared count, run out of data") applied to the wrong field: the declared count that genuinely causes EOF-style failures is the **binary** record count at the start of a `.bin` file (COLMAP binary readers do `num = read 8 bytes; for _ in range(num): ...`), not a text comment. Since you are importing text, this does not apply.

### 3. The REAL trigger: empty POINTS2D + header-only points3D.txt (strongly supported)
Multiple independent lines of evidence converge:

- **The note.com/kozosoken guide** (published 2026; walks Metashape → COLMAP → RealityScan) exists specifically because RealityScan needs the observation graph. Its core tool, `rebuild_colmap_tracks.py`, *"recreate[s] the POINTS2D (2D observations on images) in images.txt and the TRACK (observation links) in points3D.txt"* from existing poses and 3D points. The successful import shows fully populated data: *"Number of cameras = 3738, number of points = 53735, total projections = 537350, average track length = 10.000000, alignment engine = imported."*
- **Epic forum user AVsupport (Peter Graf, author of pose2colmap.py)** reports the same failure class and states it is *"partially caused by spaces at the end of the lines, and by empty lines at the end of the script,"* and that RealityScan only accepted his files after he produced a dedicated "COLMAP_RS2" output variant. He also noted RS "doesn't wanna see it … only when you delete points3d.txt contents" — i.e., the header-only path is precisely what fails.
- **Contrast with COLMAP's own FAQ**, which for the "known poses, then triangulate" workflow says the OPPOSITE. COLMAP FAQ ("Reconstruct sparse/dense model from known camera poses," colmap.github.io/faq.html): *"If the camera poses are known and you want to reconstruct a sparse or dense model of the scene, you must first manually construct a sparse model by creating a cameras.txt, points3D.txt, and images.txt,"* with the further instruction that *"The points3D.txt file should be empty while every other line in the images.txt should also be empty."* That empty-form guidance is for feeding COLMAP itself (which then computes features) — **RealityScan's importer does NOT behave like COLMAP's and requires the populated form.** This is exactly why your empty/header-only attempts (both variants) all failed.

### 4. Non-consecutive image names / IDs (assessment)
There is no evidence RealityScan requires consecutive or gap-free filenames. COLMAP's own format doc states: *"the unique identifiers of cameras (CAMERA_ID), images (IMAGE_ID), and 3D points (POINT3D_ID) are unordered and are most likely not contiguous."* Your decimated names (img_00000, img_00005, …) with consecutive IMAGE_IDs are fine, provided the referenced image files exist and the model is internally consistent. **This is not your cause.**

### 5. Confirmed-working minimal model shape
Every working example produces a FULLY populated, mutually-consistent model — images.txt with real POINTS2D rows, points3D.txt with real points and TRACKs. In TakashiYoshinaga/360-to-RealityScan (which emits cameras.txt/images.txt/points3D.txt that RealityScan accepts), points3D.txt is *"generated only when a PLY file is specified,"* and the tool's primary RealityScan path actually pairs images with XMP sidecars for pose. **There is no published example of a header-only/empty three-file set importing successfully into RealityScan 2.1.**

### 6. What rebuild_colmap_tracks.py produces
Per the note.com guide, the script takes an existing text model (cameras.txt intrinsics, images.txt poses, points3D.txt with XYZ+RGB) and, by geometric projection of each 3D point into each camera using the known poses and intrinsics, generates (a) the POINTS2D list (2D x,y + point3D_id) on the second line of every image in images.txt, and (b) the TRACK list of (image_id, point2d_idx) pairs appended to every point in points3D.txt. It does NOT re-run SIFT or matching. Example output: 53,735 3D points, 0 dropped, 537,350 observations, mean track length 10.0. The author's stated conclusion: *"This procedure does not restore the original SIFT features or descriptors/matches. It is a method of reconstructing the observation graph through geometric projection from existing camera poses and 3D points, and then handing it over to RealityScan for mesh generation."* This directly confirms your hypothesis #6: **the real requirement is populated points3D + POINTS2D observations, and the empty approach fundamentally does not work.**

### 7. The definitive XMP exact-priors alternative (recommended)
Per the official RealityScan Help "XMP Metadata Files" page and confirmed by Epic staff on the forums:

- **Association:** Each image gets a sidecar XMP with the SAME basename (Image01.jpg → Image01.xmp) in the same folder; RealityScan auto-associates them on import (*"If placed in the same folder, an image and an XMP file with the same name will act as one when imported"*). A single `_common.xmp` can apply the same data to all images in a folder.
- **Structure** (namespace `http://www.capturingreality.com/ns/xcr/1.1#`): an `rdf:Description` with `xcr:Version="3"`, `xcr:PosePrior="locked"`, `xcr:Coordinates="absolute"`, intrinsics (`xcr:FocalLength35mm`, `xcr:PrincipalPointU/V`, `xcr:DistortionModel`, `xcr:DistortionCoeficients`, `xcr:Skew`, `xcr:AspectRatio`), plus child elements `<xcr:Rotation>9 values</xcr:Rotation>` and `<xcr:Position>3 values</xcr:Position>`.
- **xcr:Rotation** is a 3×3 rotation stored **ROW-MAJOR** (first three numbers = first row) and is the **WORLD-TO-CAMERA** rotation R — verified by an Epic/Capturing Reality developer (OndrejTrhan) quote in the "XMP Rotation" forum thread.
- **xcr:Position** is the camera **CENTER C in world coordinates** (NOT the translation vector t) — verified via a developer-confirmed working reprojection example in the "Camera Parameters in the output XMP file" thread, where the working code derives `t = −R·Position`.
- **COLMAP → XMP conversion:** `R_xmp = R_colmap` (row-major flatten of the world-to-camera matrix), and `Position = C = −R_colmapᵀ · tvec`. The center transfers robustly; the rotation MAY need a fixed axis-swap matrix B (empirically `B = R_rc · R_colmapᵀ`) because RC's and COLMAP's camera-axis conventions can differ — the widely-reported "cameras explode / point outward / determinant −1 chirality" problem.
- **PosePrior values** (verbatim from RealityScan Help): *draft* = *"absolute camera positions, but they are subject to adjustment during the alignment process"*; *exact* = *"ensures that the cameras maintain their relative positions"*; *locked* = *"combines the preservation of both relative and absolute camera positions … the positions remain fixed and are not adjusted during the alignment phase."* **Use "locked" for known immovable poses.** Pair with `xcr:CalibrationPrior="exact"` if intrinsics are also fixed. The Export Registration save type is literally labeled "RealityScan XMP (exact priors, absolute coordinates)."

Example verified real-world XMP shape (from nerfstudio issue #2383):
```xml
<x:xmpmeta xmlns:x="adobe:ns:meta/">
 <rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#">
  <rdf:Description xcr:Version="3" xcr:PosePrior="locked" xcr:Coordinates="absolute"
    xcr:DistortionModel="brown3t2" xcr:FocalLength35mm="..." xcr:Skew="0" xcr:AspectRatio="1"
    xcr:PrincipalPointU="..." xcr:PrincipalPointV="..." xcr:CalibrationPrior="exact"
```

## Details

### Why your ruled-out items didn't fix it
You correctly eliminated line endings, carriage returns, trailing whitespace, blank-line structure, and empty vs header-only points3D. All are real failure modes reported by others (AVsupport's trailing-space/empty-line findings are genuine and worth keeping fixed), but none addresses the core structural problem: RealityScan's COLMAP importer wants a complete, self-consistent reconstruction *with observations*. An images.txt where every second (POINTS2D) line is empty, plus a points3D.txt with zero points, gives the parser no observation graph to bind cameras to points — and the read that runs off the end of the file throws the ERROR_END_OF_MEDIA/EOF error. Your two points3D experiments (0-byte and header-only) are BOTH the empty case that is documented to fail.

### The two viable fixes, ranked
1. **RECOMMENDED — switch to XMP sidecars** (fast, deterministic, officially supported). You already have known poses and a single PINHOLE intrinsic, so this is a near-perfect fit. Generate one `.xmp` per image, `PosePrior="locked"`, `Coordinates="absolute"`, intrinsics from your cameras.txt, `Rotation` row-major world-to-camera, `Position` = camera center. Import the images (XMPs are picked up automatically); do NOT press Align; proceed to meshing/texturing.
2. **FALLBACK — make the COLMAP model complete.** Populate points3D.txt with real 3D points (from your Metashape/LiDAR cloud) and rebuild the POINTS2D + TRACK observation graph (`rebuild_colmap_tracks.py` or equivalent), then re-export from COLMAP so all files are consistent, and open cameras.txt as "Colmap Text Format" (RealityScan reads the sibling images.txt/points3D.txt from the same folder automatically).

### Intrinsics detail for your case
Your cameras.txt uses PINHOLE with fx, fy, cx, cy = 848.759, 849.231, 921.002, 565.962 at 1920×1200. If you go the XMP route, convert to the XMP intrinsic convention: `FocalLength35mm` derived from fx and sensor width, principal point offsets `PrincipalPointU/V` expressed relative to image center and normalized by the larger image dimension (RealityCapture's normalization; a known source of the "max vs min dimension" ambiguity flagged in the XMP Camera Math discussion — verify by reprojection). AspectRatio = fy/fx ≈ 1.0006. Because fx≈fy and cx,cy are near center, a small error here is low-risk, but validate on a subset.

### Version note (verified)
RealityScan 2.1.1 (April 2026) specifically improved COLMAP interchange. Per Epic's release notes and DIGITAL PRODUCTION (April 6, 2026): it *"added support for the FULL_OPENCV camera model during COLMAP imports,"* and export *"now supports both a flat folder structure and the standard COLMAP directory layout … binary or ASCII format,"* plus fixes to mask export and distorted-image export quality. If you are on 2.1.0, upgrading to 2.1.1 may change import behavior. Epic staff (JakubVanko) were actively debugging COLMAP import failures with community members (AVsupport) as of May 2026, so this remains an area of active vendor attention.

## Recommendations

1. **Immediately: switch to XMP exact priors.** For each of your 422 images, write a sidecar `.xmp` (same basename) containing `PosePrior="locked"`, `Coordinates="absolute"`, your PINHOLE intrinsics, a row-major world-to-camera `xcr:Rotation`, and `xcr:Position` = camera center (`C = −R_colmapᵀ·tvec`). Import images, verify camera positions load, do NOT align, proceed to mesh. **Change this recommendation only if** the poses turn out wrong after the axis-convention check in step 2.
2. **Validate the rotation convention on a 3-image subset FIRST.** Because of the documented RC↔COLMAP axis/chirality difference, test three images before committing all 422. If cameras "explode," point outward, or mirror, apply an axis-swap matrix — start with B = diag(1, −1, −1) (flip the y and z camera axes), i.e. `R_xmp = B · R_colmap`, and re-test. **Benchmark to proceed:** cameras form a coherent arc/path matching your capture, and a known 3D point reprojects onto the correct image pixel. If still wrong, solve B empirically by aligning a few images in RS and computing `B = R_rc · R_colmapᵀ`.
3. **If you must stay on COLMAP text:** populate points3D.txt with real points (from your existing cloud) and rebuild POINTS2D/TRACK so the model is complete and consistent, then re-export via COLMAP's "Export model as text." **Threshold to declare success:** RealityScan's component panel reports nonzero points, nonzero total projections, and mean track length ≈ your points-per-image, with alignment engine = "imported."
4. **Housekeeping regardless of path:** keep trailing spaces stripped, remove trailing blank lines at EOF, keep Unix `\n`, and ensure every NAME in images.txt corresponds to a real image file present at import (these are confirmed secondary failure modes, just not the root cause of your empty-model failures).
5. **Upgrade to RealityScan 2.1.1+** before further debugging, and if the fallback COLMAP path still fails, post your minimal repro to the Epic Developer Community thread where JakubVanko is triaging COLMAP import cases.

## Caveats
- The claim that empty POINTS2D + header-only points3D is the specific trigger is **strongly supported** by the note.com guide (whose entire existence is to fix this) and by forum reports, but is **NOT confirmed by an official Epic statement isolating that exact field** — Epic has published no formal spec of what its COLMAP importer requires. Treat it as best-supported inference, not vendor-documented fact.
- The header-count hypothesis is assessed as **very unlikely** but cannot be 100% excluded without source access to RealityScan's closed parser. The strongest evidence against it is the universal COLMAP convention that `#` lines are ignored, confirmed verbatim in COLMAP's docs.
- The XMP facts (Rotation = row-major world-to-camera; Position = camera center; PosePrior semantics) are **verified** via Epic developer forum posts, a confirmed-working reprojection example, and the official RealityScan Help. The exact COLMAP→XMP rotation mapping may require an empirically determined axis-swap matrix per pipeline (chirality) — **verify on a subset before scaling to 422.**
- Forum posts cited (stiv2804, AVsupport/Peter Graf, JakubVanko, OndrejTrhan) are practitioner/staff reports, not controlled tests. The note.com workflow was demonstrated on a 3,738-image Metashape dataset, not your specific 422-image decimated set — the mechanism generalizes, but exact numbers will differ.
